The trigger — found

Two config changes landed at the exact onset of Bug A (our client archives every hello_ok config per key):

Config changeFirst seenStorm onset
stale_order_ticks=0 (new key)08-25 ~23:2008-25 23:33
tick_seconds: 0.25 → 0.408-25 ~23:30

But the measured tick never changed: 3.998–4.001 ticks/s across every multi-hour window, and exactly 4.000 ticks/s post-reset. The server advertises 0.4 s ticks while running 0.25 s ticks. Any action-freshness window derived from the advertised value misjudges by 1.6× — fitting the erratic rejections, the load sensitivity, and why (post-reset) only WillMorr's own bot is fielding while every external guild sits in the village. Suggested grep: wherever the deploy that introduced stale_order_ticks computes action staleness from configured tick_seconds while the game loop still runs the old constant.

Working model: two independent rules. (1) An order rule: an action older than the character's last accepted action is silently dropped. (2) An envelope-age rule with a window >21 ticks whose violation returns the loud stale_frame — which storm-era frames (100–330 ticks old) always violate. Pair sample n=2, both consistent (fresh lands, aged silently dropped).

The migration (2026-08-28) — a natural experiment

The server moved to new hosting (now a DigitalOcean box) after Will reported the old network was slow with frequent packet timeouts. A host swap with the software held constant is exactly the experiment that separates network causes from server-side causes: whatever the network caused should vanish; whatever survives is not the network. Measurements below compare the storm era (runs 224–230, old host) against the first ~4 hours post-migration (run 288, 53k ticks).

This is consistent with the mechanism a lossy uplink predicts: TCP backpressure grows the server's per-connection outbound queue, so frames are delivered late-but-in-order per session, re-hello (new socket, empty queue) is curative, and client reconnect churn accumulates half-dead sessions. If Bug B was a timeout-driven cleanup culling sessions the network made look dead, it should stay gone now — worth confirming after a few days.

The tick-rate shortfall is the sharpest discriminator: a slow network cannot slow the simulation's own tick counter. The old box held exactly 4.000 ticks/s through the very worst of the storms; the new one runs 9.5% slow around the clock — the game loop is exceeding its 0.25 s budget, which reads as a compute ceiling on the new host (small droplet / CPU steal). And it recreates the pattern from the trigger section in a new form: the server again advertises one tick length while running another, so anything that converts stale_order_ticks or staleness windows to wall time via the advertised value misjudges by ~10% continuously.

Verdict: the slow network was the amplifier, not the root cause. It explains the catastrophic magnitude (hundreds of ticks of queue debt, born-stale sessions, the restart overshoot) and those symptoms died with it. What remains is the combination that still zeroes external play: a persistent per-session delivery debt of ~20 ticks, meeting stale_order_ticks=0 — zero tolerance converts even the healthy-network debt into blanket rejection. If that config was a mitigation for the old network, it has outlived its reason: restoring stale_order_ticks to a tolerant value (≥ the old default) would likely give external guilds their field time back immediately, even before the tick budget is investigated.

Post-migration probe results (2026-08-28 afternoon)

New: action validation contradicts every readable view of character state

With the debt sensor made truthful, our probe pairs (one normal + one forward-stamped village say, different characters, same batch) began drawing not_in_village — both halves, stamp irrelevant. A watcher then paired every such rejection with a same-second read of the public roster: 25 of 25 samples show the validator rejecting “not in village” while the roster endpoint simultaneously reports that character in the village (tightest pair: rejection at tick 3581303 vs roster read at 3581315). The same afternoon, a ~300-tick storm rejected ~1,000 village moves the same way (ticks ~3573100–3573400) with all 18 characters at home by every readable view. One repeat offender (c19871) never left the village at all — which suggests the divergent state lives on the session (e.g. an active-world/route entry that a re-hello or embark burst leaves pointing at a field world), not on the character. Same split-state family as Bug B’s “deleted but still rendering.”

Bug B is reduced, not gone

Character c20055 embarked at tick 3581852, embarked again at 3585717, then disappeared from the public roster with no death event ever delivered — verified after the stream fully caught up (offset 16, zero pending rejections). Either the deletion sweep still runs (now targeting characters in transit) or the death-event emission is lost on the embark path; both are server-side. A separate character (c20054) died the ordinary way in the same window and its death event arrived fine, so event delivery as such works.

Forward-stamp verdict (whether lag-corrected envelope ticks would be accepted where frame-tick stamps are rejected): still inconclusive — every clean sample so far was masked by the not_in_village rejection above, which ignores the stamp entirely.

Suggested places to look

  • Per-guild frame assembly / send path: anything O(n) in a per-guild registry that never GCs deleted characters would make our frame build exceed the tick budget precisely after Bug B churned ~100 characters through this guild in a day. The onset timing matches.
  • Session GC: whether DEALER identities from superseded sessions still get frames prepared/diffed. We created dozens overnight (self-heal reconnects); clean windows shrank as they accumulated.
  • The deletion path itself: whatever removes these characters skips the death-event emission and sometimes leaves them rendering in world frames. Batches + consecutive uid ranges suggest a sweep/cleanup job rather than gameplay.
  • Timing correlation: both bugs first appeared within hours of the 2026-08-25 wire-v3 / grouped-inventory deploy window.

Client-side status (for context)

To keep the guild alive under the incident we shipped, in order: a self-healing re-hello on sustained stale_frame storms; decide-on-freshest frame consumption (zero client-added backlog); live capability alarms; and a storm shelter that benches the roster while actions are being rejected (stranding deaths stopped at that point). None of these change the underlying measurements above — they only bound our losses. Everything unwinds automatically once frames arrive fresh.
